# Вариант 16: картинная галерея

Индивидуальное задание № 2 по АКОС. Я реализовал консольную многопоточную модель для Linux на C11 с использованием libc и pthread.

## Быстрый запуск

Нужны Linux, GCC и GNU Make. Для тестов дополнительно нужен Python 3 (стандартная библиотека).

```bash
make
./gallery
```

По умолчанию: 200 посетителей, 5 картин, вместимость галереи 10, по 2 места у каждой картины. Интервалы появления 1–5 мс, осмотр 5–15 мс. Программа автоматически завершается после обработки всех посетителей. События и итог записываются в `gallery.log` (существующий файл перезаписывается).

```bash
# Медленная наглядная демонстрация
./gallery --visitors 20 --capacity 4 --paintings 3 \
  --picture-capacity 1,2,1 --arrival-min 100 --arrival-max 300 \
  --view-min 500 --view-max 1000 --seed 16

# Конфигурация из файла; аргументы CLI имеют приоритет
./gallery --config examples/bottleneck.conf --visitors 200

# Та же модель с условными переменными вместо семафоров
./gallery_cv --config examples/default.conf

# На экран только итог; полный журнал сохраняется
./gallery --quiet --log run.log

# Не создавать файл журнала
./gallery --log none

./gallery --help
```

`Ctrl+C` / SIGINT и SIGTERM прекращают новые прибытия, отменяют ожидания и незавершённые осмотры. Все занятые места освобождаются, потоки соединяются через `pthread_join`, сохраняется итог. Частичный осмотр не засчитывается. SIGUSR1 зарезервирован для внутреннего завершения потока сигналов.

## Параметры

| Параметр | По умолчанию | Допустимые значения |
| --- | --- | --- |
| `--capacity` | 10 | 1..1000 |
| `--paintings` | 5 | 1..100 |
| `--picture-capacity` | 2 | 1..1000; одно число или ровно по числу картин |
| `--visitors` | 200 | 0..1000; 0 означает пустой рабочий день |
| `--arrival-min`, `--arrival-max` | 1, 5 | Миллисекунды, 0..60000, min <= max |
| `--view-min`, `--view-max` | 5, 15 | Миллисекунды, 0..60000, min <= max |
| `--strategy` | random | random / sequential |
| `--seed` | 16 | 0..4294967295 |
| `--config` | нет | Файл key=value, один на запуск |
| `--log` | gallery.log | Путь или none |
| `--quiet` | выключен | На stdout остаются только итоги |
| `--help` | — | Справка |

В конфигурации используются те же имена без `--`; `quiet=0` / `quiet=1`. Пробелы вокруг `=` и комментарии после `#` допустимы. Пустой файл оставляет значения по умолчанию. Относительные пути считаются от текущей рабочей директории. Нулевые вместимости, ноль картин, отрицательные числа, неизвестные ключи и ошибочные диапазоны отвергаются до создания потоков. При нехватке системных ресурсов программа останавливает уже созданные потоки и возвращает ошибку.

`random` создаёт перестановку всех картин; `sequential` задаёт порядок 1, 2, ..., M. Если выбранная картина занята, посетитель ждёт именно её, не удерживая место у другой картины. Одинаковые параметры и `seed` дают одинаковые планы прибытия и осмотров; порядок исполнения потоков и временные метки могут различаться.

Коды завершения: 0 — успех, 1 — ошибка выполнения/ввода-вывода, 2 — неверные параметры, 130 — SIGINT, 143 — SIGTERM. При ошибке выполнения и одновременном сигнале приоритет имеет код 1. Бесконечный режим не реализован: выбран завершаемый вариант рабочего дня, прямо разрешённый условием.

## Проверка

```bash
make test
# или
bash tests/run_tests.sh

# Расширенный аудит: стресс, границы, системные отказы, статический анализ
make audit

# Проверки AddressSanitizer + UndefinedBehaviorSanitizer
make sanitize

# Проверка гонок данных ThreadSanitizer
make thread-sanitize
```

В ограниченной среде, где LeakSanitizer не может читать `/proc`, предусмотрен явный вариант:

```bash
make sanitize SANITIZER_EXTRA=tests/no_lsan.c
```

Он отключает только LeakSanitizer. Основная сборка от этого файла не зависит. Сборка ASan/UBSan использует -fno-sanitize-recover=all, чтобы диагностированное нарушение не оставалось успешным запуском. В приложенном отчёте указано, какие проверки фактически выполнены. Тесты восстанавливают состояние модели по журналу: проверяются лимиты, FIFO выдачи разрешений, отсутствие одновременного осмотра двух картин, повторов и утечек занятых мест; это не проверка одного лишь кода возврата.

При повторной проверке я выполнил 110 основных проверок, 118 расширенных, 110 запусков с ASan/UBSan и 110 с ThreadSanitizer. Все проверки прошли. Описание проверенных требований и результатов — в `AUDIT.md`. ФИО и группу в отчёте нужно заполнить перед сдачей.

## Состав проекта

При оформлении C-кода я использовал следующие правила: все ветки `if`/`else` заключены в фигурные скобки, каждая инструкция находится на отдельной строке, `++` и `--` записаны после операнда. Те же правила я применил к тестовым C-файлам. Результат проверки стиля находится в `results/style-check.json`.

- `src/main.c` — потоки, очередь, модель, журнал, сигналы, статистика.
- `src/config.c`, `src/config.h` — CLI и файл конфигурации, проверка входных данных.
- `src/sync.c`, `src/sync.h` — основная реализация с семафорами и альтернативная с условными переменными.
- `tests/` — автоматические проверки и скрипт запуска.
- `examples/` — готовые наборы параметров.
- `results/` — реальные журналы и результаты тестирования.
- `REPORT.md`, `REPORT.pdf` — отчёт; **перед сдачей впишите ФИО и группу**.
- `AUDIT.md` — повторная сверка требований, найденные пробелы проверок и результаты аудита.
- `tools/build_report.py` — создание PDF из отчёта; нужен пакет reportlab и шрифты DejaVu.

Для повторной сборки PDF после заполнения полей: `python3 tools/build_report.py`. Установка reportlab нужна только для пересоздания PDF, не для компиляции программы или запуска тестов. В ZIP включены исходники, а не бинарные файлы: соберите обе программы командой `make` в Linux.
