# Моделирование рабочего дня картинной галереи

**Индивидуальное домашнее задание № 3 / Вариант 16**

**Группа:** 252

## Условие задачи

Галерея ограничивает число посетителей в зале и число зрителей около каждой картины. Люди прибывают через случайные интервалы. Если все места в зале заняты, посетитель ждёт в очереди, пока вахтёр разрешит вход.

Войдя, посетитель выбирает ещё не осмотренную картину. Если возле неё нет места, он ждёт там же. После осмотра всех картин посетитель выходит. Вахтёр закрывает вход, когда вошёл последний посетитель, и завершает рабочий день после последнего выхода.

## Участники модели

Вахтёр и каждый посетитель выполняются в отдельных процессах Linux. Посетитель определяет свой маршрут, выдерживает паузы и отправляет события вахтёру. Вахтёр распределяет места и ведёт журнал. Картина представлена номером, лимитом мест, счётчиком зрителей и очередью.

## Консольный журнал

Вахтёр выводит события в порядке обработки. Строка содержит номер события, время в миллисекундах, номера посетителя и картины, число занятых и зарезервированных мест и пояснение по-русски. Ключ `--log` сохраняет те же строки в файл.

## Синхронизация процессов

### Запросы и разрешения

Перед открытием каждый посетитель регистрируется. Когда зарегистрированы все N процессов, вахтёр передаёт им время открытия, параметры задержек и начальное значение генератора. Первый плановый приход совпадает с открытием. Время каждого следующего равно времени предыдущего плюс случайный интервал.

В реализациях с общей памятью `shm_open`, `ftruncate` и `mmap` с `MAP_SHARED` создают область для запроса и плана дня. Семафор `EMPTY` разрешает записать следующий запрос, `FULL` будит вахтёра после записи. Он читает запрос и возвращает `EMPTY`. Отдельный семафор каждого посетителя передаёт персональное разрешение.

В версии с неименованными семафорами `sem_init` получает `pshared = 1`. В остальных версиях процессы получают семафоры через `sem_open`. В версии FIFO запросы идут по каналу `requests`, копии общего плана — по каналу `plans`. Каждое сообщение помещается в одну атомарную запись в канал.

### Допуск в зал и к картинам

Вахтёр выдаёт место первому ожидающему у входа. Между разрешением и фактическим входом место зарезервировано. При входе вахтёр переносит единицу из `reserved` в `hall`. При выходе он уменьшает `hall` и сразу проверяет входную очередь.

У каждой картины своя очередь в порядке поступления запросов. Выбранная стратегия задаёт последовательность картин. По завершении осмотра вахтёр освобождает место, отмечает картину у посетителя и может допустить первого ожидающего.

### Проверяемые ограничения

| Инвариант | Как его поддерживает модель |
| --- | --- |
| Вместимость зала | Разрешение выдаётся, пока `hall + reserved` меньше вместимости. |
| Лимит у картины | Перед `BEGIN` число зрителей сверяется с лимитом выбранной картины. |
| Один активный осмотр | Следующий выбор допустим только после `END` предыдущего осмотра. |
| Однократность осмотра | Битовая маска хранит завершённые картины. Вахтёр отклоняет повторный выбор. |
| Освобождение места | `EXIT` допустим после всех картин. Счётчик `hall` уменьшается ровно на единицу. |

## Запуск и завершение

Я собираю проект командой `make` из его корневого каталога. Основную программу я написал на C11 с использованием libc и системных API Linux. Для массового запуска независимых программ и автоматических тестов использую Python 3.

### Команды запуска

```bash
./bin/gallery-named --seed 42
./bin/gallery-unnamed --seed 42
python3 scripts/day.py shm --seed 42
python3 scripts/day.py fifo --seed 42
```

Для ручного сеанса откройте два терминала в каталоге проекта. В первом запустите вахтёра. Во втором, после `READY`, запустите оба процесса посетителей. Путь `./day` должен быть свободен.

**Терминал 1:**

```bash
./bin/guard fifo ./day --visitors 2 --limit 1
```

**Терминал 2:**

```bash
./bin/visitor ./day 1 &
./bin/visitor ./day 2 &
wait
```

### Параметры модели

| Параметр | Значение и диапазон | По умолчанию |
| --- | --- | --- |
| `--capacity` | Мест в зале, от 1 до 300 | `12` |
| `--paintings` | Число картин, от 1 до 64 | `5` |
| `--limit` | От 1 до 300 мест. Одно число или список по числу картин, например `1,3,2` | `3` |
| `--visitors` | Число посетителей за день, от 1 до 300 | `120` |
| `--arrival` / `--view` | Интервалы прибытия / осмотра. От 0 до 60 000 мс, число или диапазон `A:B` | `2:8` / `10:30` |
| `--strategy` | `random` — независимо перемешанный маршрут, `ordered` — картины по номерам | `random` |
| `--seed` / `--log` | Зерно генератора / путь к копии журнала | Время и PID / только stdout |

### Закрытие входа и прерывание

После последнего входа появляется `CLOSE`, после последнего выхода — `SUMMARY`. По Ctrl+C или `SIGTERM` обработчик устанавливает флаг остановки. Вахтёр сохраняет частичные итоги в журнал при заданном `--log` и выводит `STOP`, если канал вывода доступен. Родитель дожидается детей через `waitpid`. В независимом сеансе посетители обнаруживают уход вахтёра по снятию блокировки файла `ready`.

Владелец сеанса удаляет созданные имена семафоров, объекты разделяемой памяти, FIFO и каталог сеанса. В версии с `sem_init` он вызывает `sem_destroy` после завершения дочерних процессов.

Во всех четырёх журналах максимумы составили 12 человек в зале и 3 у картины. В дополнительных прогонах на 300 посетителей я получил по 1 500 завершённых осмотров. После закрытия в каждой версии `hall = 0` и `reserved = 0`.

### Две очереди в коротком примере

В `examples/queue.log` три посетителя, два места в зале и одно у картины. В строке 8 посетитель № 2 ждёт у входа. Оба места уже зарезервированы. В строке 14 посетитель № 3 находится внутри и ждёт у картины. Окончание осмотра посетителем № 1 в строке 15 позволяет № 3 начать осмотр в строке 16. Только выход № 1 в строке 17 позволяет выдать № 2 разрешение на вход.

### Автоматические тесты

Для проверки всех четырёх реализаций я использую команду `make test`. Тест отдельно восстанавливает очереди, состав зала, активные и законченные осмотры. Для каждой строки он сравнивает эти данные со счётчиками вахтёра. Я проверил постоянные и случайные задержки, обе стратегии, разные лимиты у картин, крайний случай с одной картиной и маршрут из 64 картин.

В тесте с осмотром длительностью 60 секунд я отправлял `SIGINT`. Во всех версиях процессы завершились за отведённые 5 секунд. В независимых версиях я также отправлял сигнал одному посетителю. Я убедился, что каталог сеанса и именованные объекты в `/dev/shm` удаляются.
